# Token-efficient research loop

- Apply these defaults to long-running scientific or ML research, autoresearch, iterative training/evaluation, benchmark optimization, hypothesis testing, and cluster experiment series. Do not activate them for ordinary one-off coding or debugging.
- Use the user-wide `research-loop` skill for those tasks. Start or resume from `research-manager handoff --json` when `.research/state.json` exists; initialize durable state once for a new research program. Never reconstruct research state from full Codex transcripts.
- Treat handoff, status, health, and comparison caps as context budgets, never storage limits. Raw evidence must remain untouched. Use `research-manager inspect RUN_ID --section evidence|summary|health|all --json` whenever omitted detail could affect a diagnosis or decision.
- Use GPT-5.6-Sol at `xhigh` for scientific diagnosis, hypothesis formation, experiment design, research planning, implementation specifications, result interpretation, and go/no-go decisions, including the hardest research problems. Do not lower its model or effort to save tokens. Use GPT-5.6-Sol at `high` with a read-only sandbox for routine review of Muse code, configuration, and test diffs and validation reports against the Sol-xhigh contract.
- After Sol-xhigh defines file ownership, constraints, and acceptance criteria, delegate all execution-ready research code, configuration, and test changes to the locally installed Meta Muse Spark model `muse-spark-1.2-contributor` at `xhigh` via the Muse CLI. Sol-xhigh creates the implementation contract and the read-only Sol-high reviewer reviews every resulting diff and validation report before launch; an unfavorable review produces a bounded correction request back to Muse and neither Sol patches the implementation itself; a scientific ambiguity returns to Sol-xhigh with a bounded, exact implementation-evidence handoff (with file/line references and the relevant behavior) for contract revision, Muse reimplements, and Sol-high reviews again; a favorable review hands a bounded verdict (with exact file/line references and validation evidence) to Sol-xhigh, which owns launch/go-no-go without duplicating routine review and without inspecting raw code. All code, configuration, and test review remains with the Sol-high reviewer; the Sol-xhigh lead does not inspect raw code or implementation details. The reviewer may and must assess test and validation evidence for implementation correctness, but it must not interpret scientific experiment results or make scientific decisions. Muse is the sole implementation worker; if Muse is unavailable or fails, stop and report the limitation without substituting Sol, Luna, or another model. Implementation workers never choose the science or interpret experiment results.
- Save tokens through deterministic scripts, bounded output, change-only reporting, and compact handoffs—not by lowering research reasoning quality.
- Never use an LLM to wait for a deterministic external condition. Arm `research-manager arm-monitor`, hand its exact blocking command to one `cluster_monitor` with no conversation history, then end the frontier continuation. Do not call `wait_agent`, `list_agents`, or emit no-change status updates while it waits.
- On Slurm clusters, use `cluster-manager` instead of rebuilding scheduler/log pipelines. Event monitors must use persistent state, `--until wake`, and `--timeout 0`; ordinary progress stays inside the deterministic process and never resumes an agent.
- Route new evidence in this order: deterministic classification first, bounded GPT-5.6 Luna triage only for an ambiguous material event, and the selected frontier model only for scientific or genuinely difficult reasoning. Resume the frontier agent only from a compact material wake packet.
- Route bounded one-off server, process, Slurm, GPU, and log-health checks to the Luna-low `cluster_checker`; it reports operational evidence once and never polls, modifies an experiment, or makes a scientific diagnosis. Material anomalies return to Sol xhigh.
- For recorded training runs, use `research-manager health RUN_ID --json` after initial progress, on anomalies, at completion, and before interpretation. Any warning or critical signal returns control to the main research agent for raw-evidence and code inspection; heuristics never diagnose, cancel, or choose the next experiment.
- Cluster monitoring is experiment-read-only: apart from its atomic cursor/state files, never submit, cancel, requeue, edit experiment data, or choose a scientific next step. Never reread unchanged logs, skills, handoffs, or conversation context merely to learn whether a process finished.
- If a recurring cluster operation is missing, update and test the shared manager source once and reinstall it instead of repeatedly improvising shell commands.
- Recover long-running work from current plans/results, git state, recorded evidence, and live job state. Do not load entire Codex JSONL transcripts into the active research context.
